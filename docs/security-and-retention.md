# Security and retention

FieldOps keeps private originals separate from the fictional sample workspace. The personal launcher provides one trusted buyer with a loopback-bound local server and isolated `.fieldops/personal` storage. The active cloud backend uses Neon PostgreSQL, managed Neon Auth and private Neon object storage, with Trigger processing. Hosted sign-in, private storage, parser/manual workflow and synthetic local recovery have passed the checks in [hosted acceptance](hosted-acceptance.md). Broad AI reliability and separate hosted identities remain unverified. This is not a claim of audited production security.

## Access boundaries

- Cloud APIs validate the managed Neon Auth SDK session, then recheck the actual session expiry/revocation, user ban state, linked GitHub account and active invitation in PostgreSQL on every private request without caching. Invitations use the provider-controlled numeric GitHub account ID, not email, username or editable metadata. Cached identity alone does not authorize access.
- Every private repository operation scopes records to the authenticated owner. Unauthorized IDs return unavailable/not-found responses. All application tables have RLS and no application privileges are granted to public/browser roles. Runtime read policies permit the trusted backend role; explicit server owner checks and mutation-function owner/revision/fence checks enforce personal-workspace isolation. There is no direct browser database API or per-browser JWT RLS policy.
- `FIELDOPS_DATABASE_URL` uses a restricted runtime login. Each operation sets `fieldops_server` inside the same transaction as its parameterized query. The role cannot own tables, bypass RLS, directly insert comparisons/documents, edit invitations or execute internal snapshot/budget helpers. Integration-managed `DATABASE_URL` is administrative and is deliberately ignored by runtime code. All database and storage credentials are server-only; never use `NEXT_PUBLIC_` names.
- Managed Auth SQL grants expose only identity, account-link and session ID/user/expiry columns needed for authorization. Runtime queries cannot read passwords, OAuth tokens or session token values. Live permission inspection confirmed direct comparison insertion and managed session-token reads are denied; hosted cross-user behavior still needs acceptance.
- Mutations check same-origin browser requests. OAuth uses the fixed `FIELDOPS_SITE_URL` and an exact Neon Auth trusted origin. GitHub returns to the branch Auth provider callback; managed sign-in then returns to the app's `/auth/callback`. The Neon SDK handles the signed-cookie and one-time session handoff with a separate random cookie secret of at least 32 characters. No arbitrary return URL or client-held database credential is accepted.
- Local mode requires explicit configuration and loopback URL/Host values. Next's automatically inserted forwarding headers are accepted only for matching loopback authorities and a single loopback client; remote forwarding and chains are rejected. `npm run personal` binds to `127.0.0.1` on a free port from 3001–3009, never uses port 3000, and does not stop another process to free a port. Ordinary dev/start scripts also bind to loopback. Do not tunnel or publicly bind local mode: headers are not a substitute for the network boundary.
- Personal and sample workspaces have separate views and creation flows. Personal comparisons remain in the local/server repository; only records marked as fictional samples are saved under `fieldops-demo-v1` in browser storage. Sample comparisons do not accept private uploads. Resetting samples preserves personal comparisons.
- Runtime readiness returns flags and recovery reasons, never credentials. Public demo visitors cannot create private uploads through an unconfigured server.

## Private files and source links

Originals use opaque document IDs, SHA-256 integrity checks and owner-prefixed storage paths. The cloud `quotations` bucket must be private. A five-minute signed PUT permits only the intended staging path, `<owner>/<document>.upload`, with signed content type and size. It is replayable during its lifetime; it is not a one-use token. The timestamp starts at request admission, so a delayed signer cannot extend the deletion replay window. Bucket CORS permits the exact deployed application origin.

Finalize validates the saved owner and upload state, checks exact HEAD size before downloading, bounds the actual stream and verifies SHA-256 before saving the canonical `<owner>/<document>` source. A browser never receives a canonical PUT URL. Existing canonical bytes must match the admitted hash/size; legitimate concurrent finalizations can save identical bytes only. Conditional `If-None-Match` enforcement is not assumed because Neon has not established it for this integration. Access keys, upload URLs and storage response details must not be logged or shared. Storage timeout and integrity failures preserve saved application state for recovery.

Every source request first checks ownership. Local sources return private, noncacheable responses, with `nosniff` and a sandbox policy. Cloud sources redirect to a signed storage URL valid for **60 seconds** to avoid proxying large files through a web function. Anyone possessing that temporary URL can use it during its validity period; expiry is not an identity check. Do not include signed URLs in logs, exports, analytics or screenshots. Exports keep application/source references rather than temporary signed URLs.

## Document trust and model handling

Quotation contents are untrusted data. Parsing does not execute spreadsheet formulas or embedded document code. The model request frames source material as data, uses structured outputs and exposes no external tools. Returned fields and source IDs are validated; deterministic code handles arithmetic and comparability constraints. Instructions inside a quotation cannot authorize supplier contact, account changes or access to another document.

The current release defaults to `FIELDOPS_PROCESSING_MODE=parse_only`. Cloud upload admission does not require a model key: an authenticated owner, configured private storage and worker are sufficient. Each document and run records its selected processing mode; retries cannot promote a parser-only upload to AI processing. Legacy local records default missing modes to parser-only; the active Neon migration enforces pinned document/run modes and terminal-state fences. Complete source parsing ends in the terminal `source_ready` state; unreadable coverage remains partial. Neither state claims that an AI model extracted quotation fields.

Manual review records the buyer's current assessment and reason. Completion requires readable source coverage, a supplier name and at least one entered item. The buyer is asked to check every original section and relevant commercial term; the application cannot prove that the buyer entered every item correctly. Added items or corrections reopen manual review. Arithmetic discrepancies, unavailable sources and incompatible commercial conditions remain separate checks.

Local AI development is configured with the verified Groq Free account and Inference APIs ZDR. Tiny synthetic extractions passed, but larger probes still fail; hosted AI remains disabled with no production model key. Activation requires explicit AI processing mode, a supported Groq model, a key, Free Plan confirmation and Zero Data Retention confirmation in each applicable runtime. The flags express operator confirmation, not proof of provider-account settings. When activated, bounded source chunks and matching inputs are sent to the configured provider. Check its current Data Controls first; ZDR governs customer content, while provider usage metadata has separate retention. [Groq data handling](https://console.groq.com/docs/your-data).

The personal launcher defaults to parser-only mode and clears model/cloud credentials from its child environment, including inherited shell values; it does not edit configuration files. Explicit `--ai` loads only the separately validated model settings from `.env.ai.local`. Desktop subscription credentials are never an alternative. No paid fallback is implemented. Live prompt-injection resistance and broad semantic source correctness remain unverified until real evaluation.

Processing limits bound document size, page/cell counts, image pixels, item counts, concurrency, duration and retries. These reduce resource risk but are not a full sandbox against every malicious parser input. The private pilot should remain invited and use the documented supported inputs.

## What is retained

| Data | Current retention behavior |
| --- | --- |
| Public synthetic originals/fixtures | Kept in the repository/deployment as demo assets; contain no real supplier documents |
| Demo edits | Fictional sample records only in this browser's `localStorage` under `fieldops-demo-v1`; clear site data to remove the browser copy |
| Local originals, parsed source spans, runs, extraction versions, corrections and checkpoints | The personal launcher uses `.fieldops/personal`, separate from test data; `--data` can select a restored/custom directory. Ordinary local mode still uses `.fieldops` or `FIELDOPS_DATA_DIR`. Records persist until document/comparison deletion |
| Current manual-review acknowledgement | Stored with the quotation's review issues; later changes reopen the acknowledgement, and deletion removes it with the quotation |
| Cloud equivalents | Persist in the dedicated private Neon bucket and PostgreSQL until document/comparison deletion; hosted parsing/storage and a synthetic local recovery drill have passed |
| Failed or cancelled work | Original and completed parse/chunks remain for review or retry; cancellation does not delete files |
| Unfinished cloud upload intent | Finalization expires after 24 hours. Bounded cleanup removes the placeholder and queues private-object deletion; pauses can delay the sweep |
| Cloud deletion tombstone | Retained for at least six minutes and until a subsequent canonical/staging deletion succeeds; a paused cleanup worker extends retention |
| Downloaded workbook / saved PDF | Stored by the buyer outside FieldOps; deleting a comparison cannot recall downloads |
| Personal backup directories | State and referenced originals remain in the chosen private destination until the buyer removes that backup; app deletion does not remove older copies |
| Compute budget reservations | Minimal amount/time records persist after deletion so deleting work cannot bypass the free budget |

There is **no automatic age-based purge** of completed private originals, parsing results, checkpoints or backups in this release. Browser exports are generated on demand and not archived by the server. The 24-hour expiry applies only to unfinished cloud upload intents; it never deletes completed quotations. Workspace/project admission reserves original-file bytes atomically, including pending deletion until cleanup succeeds. Derived database records and history need separate monitoring; original-file limits are not a database-size guarantee. See [Neon limits](../neon/README.md#pilot-capacity-and-expiry) and [hosted recovery](cloud-recovery.md).

## Deletion and backups

Deleting a document removes its active application record, parsed evidence, jobs, checkpoints, extraction records and related correction data. Other quotations remain. Groups referencing deleted rows are updated and require review. Cloud comparison snapshots containing a deleted source are removed to avoid retaining the original text through history. Deleting a comparison removes all its related private application data.

Object removal is placed in a persisted deletion outbox and attempted immediately. App access is revoked as soon as the database/file transaction commits; a previously issued source URL can remain usable until its 60-second expiry if storage deletion is delayed. Cancellation alone preserves the original and completed source work.

Cloud deletion removes both canonical and staging paths but keeps its tombstone for **at least six minutes**, covering the maximum five-minute upload-ticket lifetime plus a margin. The runtime DELETE policy prevents early removal of that tombstone. A later sweep repeats both object deletions before removing the aged record, covering staging bytes replayed after the first deletion. The reconciliation task runs every 15 minutes, processes at most 50 records, and retains failed deletions for another attempt. Six minutes is a minimum retention period, not a guaranteed completion deadline. A request already accepted by the storage provider may outlive URL expiry; actual provider timing/replay behavior remains part of hosted acceptance.

Local failures are retried by the local runner. Cloud cleanup requires a deployed, active worker and available free capacity; an unconfigured, paused or exhausted service cannot perform background deletion. Maintenance expires at most 25 unfinished uploads older than 24 hours before draining the deletion outbox. Finalization rejects an expired intent even before that sweep. Completed uploads are never expired. Successful finalization attempts staging cleanup; a failed cleanup can leave staging bytes until later explicit document deletion. There is no bucket-wide orphan scan.

Deletion is not a secure-erase guarantee for operating-system snapshots, manually copied local backups, exported reports or provider-managed backups/logs. Apply the hosting providers' retention policies to those copies. Local data is stored with restrictive creation modes where the OS supports them; Windows directory ACLs still determine actual access. Keep `.fieldops` and `.env.local` out of shared folders and version control.

For personal backups, stop the session and run `npm run personal:backup`. The tool takes the local state lock, copies saved state and its referenced originals into a new directory, and checks original hashes and sizes. It excludes environment files, credentials, caches, OCR assets, browser-only samples and unreferenced loose files. A running personal session or unfinished upload blocks backup.

Use `npm run personal:restore -- --input="BACKUP-DIRECTORY" --verify` to verify every file without restoring. Restore without `--verify` creates a new directory and refuses existing destinations; it validates manifest paths, rejects symlink traversal and rechecks copied bytes. Failed operations retain `.fieldops-incomplete`, which these tools and the launcher reject. Backups are not encrypted or signed: SHA-256 detects corruption but cannot authenticate a backup against someone who can rewrite its files and manifest. See [personal backup/restore instructions](personal-use.md) and the verified [hosted-to-local recovery procedure](cloud-recovery.md). Cloud recovery history kept in active local state is scrubbed when its comparison or a related source is deleted; the separate backup copy has independent retention.

Do not edit `state.json` or delete its lock while a server is running. A corrupt state file fails closed rather than resetting saved data silently. Retain backup copies on private storage and manage their retention separately from application deletion.

## Operations and verification

Application logs contain event names, opaque run IDs, stage/error codes and attempt counts. They intentionally omit quotation text, model prompts, credentials and signed URLs. Provider SDKs/platform logs have their own policies; do not enable verbose debugging with private data without reviewing what it records.

Automated tests exercise cross-owner access, invitation/session revocation, role restrictions, cancellation fences, stale edits, deletion, pinned processing mode and terminal source readiness. Synthetic personal-tool tests cover backup/restore preservation, corruption detection, path/symlink rejection, locks and refusal to overwrite existing data. Neon SQL tests execute the actual consolidated migration in embedded PostgreSQL with only managed Auth tables stubbed from inspected types. Storage adapter tests use synthetic streams to check size/hash bounds, staging separation, ticket lifetime, retries and cleanup; they do not establish live S3 compatibility.

The dedicated Neon migration and restricted runtime have also passed a live database permission smoke check. Browser OAuth, private storage/CORS, Linux parser processing and synthetic recovery have separate [hosted evidence](hosted-acceptance.md); those checks do not establish two hosted identities, all interruption paths or broad AI reliability. [Production readiness](production-readiness.md) records the remaining gates. Report exposed credentials or cross-user access as release-blocking failures; rotate affected keys before restoring private access. Neon storage credentials require explicit revocation; do not assume a configured expiry is enforced without checking the current service. [Neon storage credential behavior](https://neon.com/docs/storage/authentication).
